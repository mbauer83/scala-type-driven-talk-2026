CHAPTER I · A SHORT HISTORY

2,500 years of trying to formalize the difference between valid and invalid reasoning.

Types are the latest expression of that project.
Your compiler's type checker is a direct descendant.

BEAT 1 · TIGHTENING THE FENCE

Each generation made the rules of valid inference more explicit, so invalid reasoning could not sneak through.

Aristotle~350 BCE · the syllogism
not "what is true" but "what follows from what"
Euclid~300 BCE · the Elements
consequences that must follow from premises — and nothing else
Frege1879 · Begriffsschrift
first predicate logic strong enough to formalize almost any mathematical claim

Formal systems restrict what can be said, so that what can be said can be trusted.

BEAT 2 · THE FENCE BREAKS · TYPES ARE THE REPAIR

Frege's system was powerful enough to eat itself.
Russell's answer, 1908: types.

Bertrand Russell1901 · paradox · 1908 · type theory

The paradox. "The set of all sets that don't contain themselves." A contradiction inside Frege's system.

The repair. Stratify the universe by type. "The set of all sets" cannot be formed — the type system will not allow it.

The safety boundary your compiler enforces was invented to stop logic from breaking.

BEAT 2b · RULES FOR REASONING · AND TWO READINGS OF "OR"

Gentzen, 1934. Natural deduction.
Introduction and elimination rules — and the moment classical and intuitionistic logic part ways.

Gerhard Gentzen1934 · natural deduction
for each connective: how to build a proof of it, and how to use one
CLASSICAL
A proof of A ∨ B is a proof that assuming ¬A ∧ ¬B is contradictory. You may not know which side is true.
INTUITIONISTIC
A proof of A ∨ B is a proof of A or a proof of B — and a tag saying which. The witness is part of the proof.
IN CODE
That second reading is exactly Either[A, B]. A value carries the tag, and you can't read it without handling both cases. The intuitionistic fragment of Gentzen's rules matches the simply-typed λ-calculus exactly.

Why this matters next slide: the type checker your compiler ships is checking intuitionistic proofs. To get a value of type Either[A, B], you must constructively supply one of the two — and the consumer must pattern-match both.

BEAT 3 · PROGRAMS ARE PROOFS · CONSTRUCTIVELY

Propositions correspond to types. A proof of a proposition
is a program of the corresponding type — an intuitionistic one.

Haskell Curry1934 onward
propositions as types — independently
William Howard1969
extends the correspondence to natural deduction
Per Martin-Löf1970s
dependent type theory — types indexed by values
When the compiler accepts…
RETURN TYPE def parseOrder(row: Row): Either[ParseError, Order]

…callers must constructively handle ParseError before they can reach an Order — the tag is the witness.

When the compiler accepts…
SIGNATURE def authorize(p: Payment[Initiated]): Payment[Authorized]

…no program reaches Authorized without constructing it from an Initiated.

Programming is constructive proof. Every time you pattern-match on Either, every time you call a function — you're discharging an intuitionistic proof obligation.

A WAY TO TALK ABOUT THE NEXT 30 MINUTES

Every invariant the business cares about lives somewhere.
The interesting question is — where.

documented

In a comment, a wiki, a Slack channel.

"Don't forget to call authorize first." True until someone forgets. The cheapest place to put an invariant — and the easiest place to lose it.

tested

In a test suite.

The test catches the bug — as long as the test exists, is maintained, and runs against the right code path. Always a sensible choice; sometimes the only choice.

encoded

In the type.

The compiler refuses to accept the invalid program. The test for this invariant can be deleted — there is no program left to test.

Over the next 30 minutes, the same invariants will migrate from the left column to the right one. That migration is what "type-driven" means in practice.

Categories worth naming out loud:

·Shape at the boundary. A function expecting Authorization isn't passed an Order or undefined.→ revisited later
·Error paths handled. The caller inspects the failure case from a constructor — not only the happy one.→ revisited later
·Exhaustive branches. Every variant of RiskDecision, PaymentMethod, RolloutState handled.→ revisited later
·Lifecycle ordering. Capture only after authorize. Release only after approve.→ revisited later
·Evidence matches verdict. A medium-risk order receives the medium-risk authorization.→ revisited later
·Boundary values. Negative or zero quantities are rejected. Empty orders are rejected.→ revisited later
·Protocol agreement. Client and server stay in step when either gains a new step.→ revisited later

STAGE 06 · TOOLKIT 1 · APPROVAL INDEXED BY RISK

The approval constructor is the proof.
Approval[LowRisk] cannot satisfy Approval[MediumRisk].

payment/Domain.scala
sealed trait Risk
sealed trait LowRisk extends Risk
sealed trait MediumRisk extends Risk
sealed trait HighRisk extends Risk

sealed trait Approval[+R <: Risk]
case object AutoApproved                          extends Approval[LowRisk]
final case class ThreeDSApproved(proof: ThreeDSProof)   extends Approval[MediumRisk]
final case class ReviewerApproved(a: ManualReviewApproval) extends Approval[HighRisk]

def authorize[R <: Risk](order: Order, approval: Approval[R]): AuthorizedPayment[R]

authorize(mediumRiskOrder, AutoApproved)
scalac Found: Approval[LowRisk], Required: Approval[MediumRisk]
story closed · bob A ThreeDSProof is required to construct an Approval[MediumRisk]. Skipping the 3DS step for a medium-risk order is no longer a valid program.

Honest aside · this specific pattern can be approximated in Java with sealed generic interfaces. What Java doesn't have is the rest of the toolkit on the next three slides — and once those are in play, Approval[R] composes with them in ways Java's type system can't follow.

STAGE 06 · TOOLKIT 2 · REFINED TYPES

The predicate lives in the type.
"Quantity is positive" stops being a constructor check.

payment/Domain.scala
type PositiveInt = Int :| Positive

final case class OrderLine(sku: String, unitPriceCents: Int, quantity: PositiveInt)

val q1: PositiveInt = 5.refine[Positive]   // ok — compile-time check on literal
val q0: PositiveInt = 0.refine[Positive]   // fails at COMPILE time
scalac Assertion failed: 0 should be strictly positive
a tool Java doesn't have Any invariant of the form "this value satisfies P" can now live in the type itself — positivity, non-emptiness, valid format, whatever the business cares about. The boundary-check class of test goes away wherever the predicate fits a refinement.
STAGE 06 · TOOLKIT 3 · PROTOCOL AS TYPE

An entire conversation, expressed as a type.
Send the wrong payload — or send when you should receive — and the build fails.

payment/Derivation.scala
type MediumRiskProtocol =
  Send[Order,
    Receive[RiskSnapshot,
      Receive[ThreeDSChallenge,
        Send[ThreeDSProof,
          Receive[AuthorizedPayment[MediumRisk],
            Receive[CapturedPayment,
              Choose[Receive[RefundedPayment, End], End]]]]]]]

// channel use:
ch.send("not an Order")         // scalac: Required CanSend[Send[Order,…]].Msg
ch.finish()                       // scalac: cannot prove P =:= End

The type CanSend[P]#Msg means "the type of the message you may send next, given the remaining protocol P". The compiler computes it from the protocol — there is no separate parameter to get wrong.

STAGE 06 · TOOLKIT 4 · DUALITY · MATCH TYPES

Server holds Channel[Dual[P]] — computed.
The two sides cannot drift, because they are not two definitions.

protocol/Dual.scala
type Dual[P <: Protocol] <: Protocol = P match
  case End           => End
  case Send[a, n]    => Receive[a, Dual[n]]
  case Receive[a, n] => Send[a, Dual[n]]
  case Choose[l, r]  => Offer[Dual[l], Dual[r]]
  case Offer[l, r]   => Choose[Dual[l], Dual[r]]
// compile-time tests
summon[Dual[LowRiskProtocol] =:=
  Receive[Order,
  Send[RiskSnapshot,
  Send[AuthorizedPayment[LowRisk],
  Send[CapturedPayment,
  Offer[Send[RefundedPayment, End],
        End]]]]]]

// every build re-runs this proof.
story closed · danielle Server and client share one protocol type. Mismatched server: compile error. No integration test could be stronger.

STAGE 06 · ASIDE · ONE TREE · MANY MEANINGS

Higher-kinded types make the recursion generic.
Two interpretations cannot drift, because there is only one fold.

payment/Rules.scala
def interpret[F[_]: Functor, A](algebra: F[A] => A)(fix: Fix[F]): A

val describe: PolicyF[String] => String = …  // human description
val analyze:  PolicyF[Analysis] => Analysis = …  // runtime snapshot

interpret(describe)(policy)   // → "card · 3DS required · refund allowed"
interpret(analyze)(policy)    // → RiskSnapshot(medium, 3ds=true, …)

Without HKTs: two separate recursions that must agree, and silently won't. With HKTs: one fold, two algebras. The compiler verifies both interpretations fit.

Idris 2.
Types depend on values.

dependent types · Π · the far corner of the cube

STAGE 07 · TWO LINKED FUNCTIONS FROM VALUES TO TYPES

Same order in. Protocol shape and approval witness — both come out.
The type of authorize is indexed by the risk the order was just assessed at.

PaymentRules.idr · PaymentDomain.idr

protocolDerivedFrom : Order n c -> SessionType

THE CLIMB

All three rungs are always populated.
The climb moves invariants between them.

documented

permanent residue

Every stage has some — coding conventions, design notes, prose policy. The amount shrinks as we climb, but never to zero.

tested

the workhorse

Most engineering teams live here for most invariants — and that is a sensible place to be. The climb shrinks which invariants need to live here, not whether tests do.

encoded

the ceiling that keeps moving

Each rung relocates a new class of invariant from a comment or a test into a compile-time obligation. Where that ceiling sits is the choice the stage makes.

"Type-driven" is the steady migration of specific invariants rightward — at whatever rung suits the cost of getting them wrong.

BEYOND TONIGHT · STILL WITHIN SCALA 3

The frontier is still moving.
There is one more rung you can already use.

SCALA 3 · CAPTURE CHECKING def withResource[T](r: Resource^)(body: Resource^{r} => T): T^{}

Resources cannot escape their scope. "This file handle is closed before the function returns" becomes a compile-time obligation rather than a defensive try-with-resources pattern. Another class of bug moving from tested to encoded.

The point is not "switch to Idris." The point is that the ladder is real, and it is available in the language you are already using.
